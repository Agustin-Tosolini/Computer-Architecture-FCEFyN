\section{Introducción}
% ============================================================

El presente trabajo documenta el diseño, la implementación y la verificación
funcional de una Unidad Aritmético-Lógica (ALU) descripta en Verilog e
implementada sobre FPGA. La consigna del Trabajo Práctico N°1 establece cuatro
requerimientos:

\begin{enumerate}[leftmargin=2em,itemsep=0.2em]
  \item Implementar en FPGA una ALU.
  \item Que la ALU sea parametrizable en el ancho del bus de datos, de modo de
        poder reutilizarse en el trabajo final de la materia.
  \item Validar el desarrollo mediante un \emph{test bench} que incluya
        generación de entradas aleatorias y código de chequeo automático
        (\emph{self-checking}).
  \item Simular el diseño con las herramientas de Vivado, incluyendo análisis
        de tiempo.
\end{enumerate}

La ALU debe soportar ocho operaciones, codificadas con el campo \texttt{funct}
de seis bits del repertorio MIPS, según la tabla que provee el enunciado. La
interfaz física con la placa es la indicada en el diagrama de bloques del
enunciado: un banco de \emph{switches} provee el dato, tres pulsadores
seleccionan a cuál de los tres registros internos (\texttt{dato\_A},
\texttt{dato\_B}, \texttt{opt}) se escribe ese dato, y el resultado de la
operación se muestra permanentemente sobre los LEDs.

El informe se organiza en tres bloques. Primero se describe la
\textbf{especificación} y la arquitectura general. Luego se analiza en detalle
la \textbf{implementación} (\texttt{ALU.v}), poniendo el foco en justificar las
dos decisiones estructurales centrales del código: el uso de una sentencia
\texttt{case} para el núcleo operacional y el uso de una cadena
\texttt{if\,/\,else if} para la captura de datos. En ambos casos el argumento no
es estilístico sino físico: se discute qué hardware genera efectivamente cada
construcción tras la síntesis. Finalmente se describe el \textbf{banco de
pruebas} (\texttt{ALU\_dut.v}), separándolo en sus capas funcionales
(definiciones, modelo de referencia, utilidades, estímulo, chequeo y secuencia
principal) y explicando qué busca demostrar cada uno de los ocho tests.

Obsérvese que los seis bits del selector permiten $2^6 = 64$ combinaciones, de

función combinacional (no queda ningún caso sin definir) y, como se verá en la
Sección~\ref{sec:case}, evita la inferencia accidental de un \emph{latch} en el
bloque operacional.

El parámetro \texttt{SHAMT\_BITS} merece un comentario. Para un dato de $N$
bits, un desplazamiento tiene sentido únicamente en el rango $[0, N-1]$; los
$\lceil \log_2 N \rceil$ bits menos significativos de \texttt{dato\_B} son
exactamente los necesarios para expresar ese rango. Calcularlo con
\texttt{\$clog2} en lugar de fijar el número 4 mantiene la coherencia del
diseño si \texttt{LENGTH\_BITS} cambia: con 32 bits el desplazador toma
automáticamente 5 bits de \texttt{dato\_B}. Además, esto acota el tamaño del
\emph{barrel shifter} a $\log_2 N$ etapas, en lugar de sintetizar un
desplazador de 16 bits de rango cuyo comportamiento para valores mayores a
$N-1$ sería irrelevante pero costoso en área.

determina la naturaleza de las estructuras físicas que se analizan a
continuación.

\section{Implementación de la ALU}
% ============================================================

El módulo completo (\texttt{ALU.v}) se reproduce en el
Apéndice~\ref{ap:alu}. Esta sección analiza sus dos bloques
\texttt{always @(*)} por separado.

\subsection{Bloque de captura: la cadena \texttt{if / else if}}
\label{sec:ifelse}

\subsubsection{El código}

\begin{lstlisting}[caption={Bloque de captura de datos con prioridad.},label={lst:captura}]
always @(*) begin
    if(i_button_1)       dato_A = i_switch;
    else if (i_button_2) dato_B = i_switch;
    else if (i_button_3) opt    = i_switch;
end
\end{lstlisting}

Este bloque decide en cuál de los tres registros se guarda el valor que está en
los switches, según qué pulsador esté activo.

\subsubsection{Por qué se usa \texttt{if / else if} y no tres \texttt{if} sueltos}

La alternativa hubiera sido escribir tres condicionales independientes:

\begin{lstlisting}[caption={Alternativa sin prioridad (descartada).},label={lst:noprio}]
always @(*) begin
    if (i_button_1) dato_A = i_switch;
    if (i_button_2) dato_B = i_switch;
    if (i_button_3) opt    = i_switch;
end
\end{lstlisting}

La diferencia aparece cuando se aprieta más de un botón a la vez. Con tres
\texttt{if} sueltos, el mismo valor de los switches se escribiría en dos o tres
registros simultáneamente. Con la cadena \texttt{if / else if}, en cambio, cada
condición sólo se evalúa si las anteriores fueron falsas, así que
\textbf{siempre se escribe un único registro}: el que corresponde al botón de
mayor prioridad. La Tabla~\ref{tab:prioridad} resume el comportamiento.

\begin{table}[H]
  \centering
  \begin{tabular}{cccl}
    \toprule
    \texttt{btn\_1} & \texttt{btn\_2} & \texttt{btn\_3} & \textbf{Registro que se escribe} \\
    \midrule
    0 & 0 & 0 & ninguno (los tres conservan su valor) \\
    1 & --- & --- & \texttt{dato\_A} \\
    0 & 1 & --- & \texttt{dato\_B} \\
    0 & 0 & 1 & \texttt{opt} \\
    \bottomrule
  \end{tabular}
  \caption{Prioridad de los pulsadores: \texttt{btn\_1} $>$ \texttt{btn\_2} $>$
  \texttt{btn\_3}. El guión indica que el valor de ese botón es indistinto.}
  \label{tab:prioridad}
\end{table}

Las razones para elegir esta versión son:

\begin{enumerate}[leftmargin=2em,itemsep=0.25em]
  \item \textbf{El comportamiento queda definido para todos los casos.} No hay
        ninguna combinación de botones que produzca un resultado ambiguo. Esto
        permite además verificarlo con el testbench (TEST 4), cosa que no se
        podría hacer si el comportamiento ante pulsaciones múltiples no
        estuviera especificado.

  \item \textbf{Los pulsadores son mecánicos.} Al apretar un botón real se
        producen múltiples rebotes, y no hay ninguna garantía de que dos
        pulsaciones ``simultáneas'' lo sean exactamente. Al escribir un solo
        registro por vez, un evento inesperado en un botón no puede afectar a
        los otros dos registros.

  \item \textbf{En hardware cuesta prácticamente lo mismo.} La prioridad se
        traduce en un par de compuertas lógicas que habilitan la escritura de
        cada registro, y quedan absorbidas dentro de las LUTs que el
        sintetizador usa de todas formas. El camino crítico del diseño no pasa
        por acá, sino por el sumador de la sección siguiente.
\end{enumerate}

\subsubsection{Sobre la inferencia de latches}

Hay una consecuencia importante de cómo está escrito este bloque, que conviene
señalar explícitamente.

El bloque es combinacional (\texttt{always @(*)}) pero \textbf{no asigna las tres
variables en todos los casos}: si no hay ningún botón apretado, ninguna de las
tres se escribe. En Verilog, cuando una variable de un bloque combinacional no
recibe asignación en todos los caminos posibles, debe \emph{conservar su valor
anterior}. Y conservar un valor requiere un elemento de memoria. Como el diseño
no tiene ninguna señal de reloj, el sintetizador no puede usar flip-flops, así
que infiere \textbf{latches}: elementos de memoria controlados por nivel, cuya
``compuerta'' es el propio pulsador.

Esto tiene un efecto observable: mientras el botón está apretado, el latch es
\emph{transparente} y su salida sigue a los switches. El valor que queda
finalmente guardado es el que había en el instante en que se \emph{suelta} el
botón, no el que había al apretarlo. El TEST 3 del banco de pruebas verifica
justamente este comportamiento.

En general se recomienda evitar los latches en diseño digital, porque complican
el análisis de tiempos y son más sensibles a los pulsos espurios (\emph{glitches})
que los flip-flops. Sin embargo, \textbf{en este trabajo la inferencia de latches
es inevitable}: la interfaz que plantea el enunciado —switches, pulsadores y
LEDs— no incluye ninguna señal de reloj, y sin reloj no hay forma de utilizar
flip-flops. Reconocemos la limitación, pero resolverla requeriría incorporar un
reloj de sistema y lógica adicional de sincronización y filtrado de rebotes, que
excede el alcance de este trabajo práctico.

\subsubsection{El atributo \texttt{clock\_buffer\_type}}

\begin{lstlisting}[caption={Atributo aplicado a los pulsadores.}]
(* clock_buffer_type = "none" *) input wire i_button_1,
(* clock_buffer_type = "none" *) input wire i_button_2,
(* clock_buffer_type = "none" *) input wire i_button_3
\end{lstlisting}

Como estas señales controlan elementos de memoria, Vivado por defecto las
interpreta como relojes e intenta rutearlas por la red de distribución de reloj
del dispositivo. Eso es indeseable: consume un recurso escaso (los buffers
globales de reloj son pocos y se necesitan para relojes reales) y obliga a
conectar los pulsadores a pines especiales. El atributo indica a la herramienta
que las trate como señales de control comunes.

\subsection{Núcleo operacional: la sentencia \texttt{case}}
\label{sec:case}

\subsubsection{El código}

\begin{lstlisting}[caption={Núcleo operacional de la ALU.},label={lst:case}]
localparam [5:0] ADD  = 6'b100000, SUB  = 6'b100010,
                 AND_ = 6'b100100, OR_  = 6'b100101,
                 XOR_ = 6'b100110, NOR_ = 6'b100111,
                 SRA  = 6'b000011, SRL  = 6'b000010;

localparam SHAMT_BITS = $clog2(LENGTH_BITS);

always @(*) begin
    case (opt)
        ADD:  result = dato_A + dato_B;
        SUB:  result = dato_A - dato_B;
        AND_: result = dato_A & dato_B;
        OR_:  result = dato_A | dato_B;
        XOR_: result = dato_A ^ dato_B;
        NOR_: result = ~(dato_A | dato_B);
        SRA:  result = $signed(dato_A) >>> dato_B[SHAMT_BITS-1:0];
        SRL:  result = dato_A >> dato_B[SHAMT_BITS-1:0];
        default: result = 16'd0;
    endcase
end

assign o_leds = result;
\end{lstlisting}

\subsubsection{Qué estructura física genera}

Hay una intuición equivocada muy frecuente al leer este código: pensar que el
\texttt{case} ``elige qué circuito construir''. No es así. \textbf{Los ocho
operadores se construyen físicamente y funcionan en paralelo, todos a la vez.}
Lo único que hace el \texttt{case} es elegir cuál de las ocho salidas llega a
\texttt{result}. El bloque se descompone en tres partes:

\begin{enumerate}[leftmargin=2em,itemsep=0.25em]
  \item \textbf{Un decodificador}, que compara los 6 bits de \texttt{opt} contra
        las ocho constantes y activa una sola señal de selección.

  \item \textbf{Los ocho operadores en paralelo.} ADD y SUB comparten un mismo
        sumador (la resta se hace sumando el complemento a dos de \texttt{B}) y
        usan la lógica de acarreo dedicada de la FPGA; es el camino más lento
        del diseño. AND, OR, XOR y NOR son compuertas independientes bit a bit.
        SRA y SRL comparten un mismo desplazador, y la única diferencia entre
        ellos es qué se rellena por la izquierda: ceros en SRL, copias del bit
        de signo en SRA.

  \item \textbf{Un multiplexor de salida} de nueve entradas (las ocho
        operaciones más el \texttt{default}), que se repite para cada uno de los
        16 bits del resultado.
\end{enumerate}

\subsubsection{Justificación: \texttt{case} frente a \texttt{if / else if}}

La misma funcionalidad podría escribirse como una cadena de nueve
\texttt{if / else if} comparando \texttt{opt} contra cada opcode. La diferencia
es estructural y se ilustra en la Figura~\ref{fig:mux}.

Los argumentos a favor del \texttt{case} son:

\begin{enumerate}[leftmargin=2em,itemsep=0.3em]
  \item \textbf{Multiplexado balanceado en lugar de cadena.} Las etiquetas de un
        \texttt{case} son constantes mutuamente excluyentes: no hay orden entre
        ellas, así que el sintetizador puede armar un árbol equilibrado de
        multiplexores. Una cadena \texttt{if / else if} expresa una prioridad
        —la rama $k$ sólo se toma si fallaron las anteriores— y eso describe
        multiplexores puestos uno detrás del otro. El árbol crece en
        profundidad de forma logarítmica; la cadena, de forma lineal.

  \item \textbf{Todas las operaciones tardan lo mismo.} En la cadena, la última
        operación atraviesa muchos más multiplexores que la primera, y el camino
        crítico terminaría dependiendo del \emph{orden en que están escritas} las
        ramas. En el árbol, el retardo de selección es parejo y el camino crítico
        queda determinado por el operador más lento (el sumador), que es donde
        tiene sentido que esté.

  \item \textbf{Se corresponde directamente con la tabla del enunciado.} Cada
        fila de la Tabla~\ref{tab:ops} es una rama del \texttt{case}, lo que
        hace inmediato revisar que estén las ocho operaciones y que ningún
        opcode esté repetido. El uso de \texttt{localparam} en lugar de números
        sueltos refuerza esto: el testbench declara los mismos ocho nombres, así
        que un error de transcripción aparece como una diferencia entre modelo y
        DUT.

  \item \textbf{La rama \texttt{default} evita latches no deseados.} Sin ella,
        los 56 opcodes no contemplados dejarían \texttt{result} sin asignar y el
        sintetizador inferiría latches, igual que en el bloque de captura pero
        esta vez sin quererlo. Con el \texttt{default}, todos los caminos
        asignan \texttt{result} y el bloque queda como lógica combinacional
        pura.
\end{enumerate}

\subsubsection{Un caso límite intencional: \texttt{opt} indeterminado}

Vale la pena señalar una consecuencia sutil del \texttt{default}. En simulación,
antes de cualquier carga, \texttt{opt} vale \texttt{6'bxxxxxx}. Ese valor no
coincide con ninguna etiqueta del \texttt{case}, por lo que se toma la rama por
defecto y la salida es \texttt{16'h0000} en lugar de \texttt{16'hxxxx}. Es
decir: la propagación de indeterminación queda enmascarada, y en la forma de
onda el estado ``sin inicializar'' se ve idéntico a un resultado válido de
valor cero. El TEST 1 del banco de pruebas está construido específicamente para
dejar constancia de este fenómeno.

\subsection{Observaciones sobre la parametrización}
\label{sec:paramobs}

El enunciado exige que la ALU sea parametrizable en el ancho del bus de datos.
El diseño lo es en su estructura general —los puertos, los registros y los
operadores están escritos en función de \texttt{LENGTH\_BITS}, y
\texttt{SHAMT\_BITS} se deriva con \texttt{\$clog2}—, pero subsisten tres
literales de 16 bits que rompen la generalidad si el parámetro cambia:

\begin{table}[H]
  \centering
  \begin{tabular}{lll}
    \toprule
    \textbf{Línea actual} & \textbf{Problema} & \textbf{Forma recomendada} \\
    \midrule
    \texttt{dato\_A = 16'b0} & ancho fijo & \texttt{\{LENGTH\_BITS\{1'b0\}\}} \\
    \texttt{dato\_B = 16'b0} & ancho fijo & \texttt{\{LENGTH\_BITS\{1'b0\}\}} \\
    \texttt{opt = 6'b0}      & ancho fijo & \texttt{\{LENGTH\_OPT\{1'b0\}\}} \\
    \texttt{default: result = 16'd0} & ancho fijo & \texttt{\{LENGTH\_BITS\{1'b0\}\}} \\
    \bottomrule
  \end{tabular}
  \caption{Literales de ancho fijo detectados en \texttt{ALU.v}.}
  \label{tab:literales}
\end{table}

Con \texttt{LENGTH\_BITS = 16} el comportamiento es correcto porque los anchos
coinciden, pero con \texttt{LENGTH\_BITS = 32} la asignación por defecto
extendería con ceros de forma implícita —lo que en este caso particular sigue
dando el resultado esperado— mientras que con \texttt{LENGTH\_BITS = 8} habría
truncamiento silencioso. La corrección es trivial y se recomienda aplicarla
antes de reutilizar el módulo en el trabajo final. Un control adicional útil es
recompilar el banco de pruebas con distintos valores del parámetro, que es
precisamente el motivo por el cual el testbench declara \texttt{LENGTH\_BITS}
como \texttt{localparam} propio en lugar de asumir 16 en todas partes.

% ============================================================
\section{Banco de pruebas}
% ============================================================

El archivo \texttt{ALU\_dut.v} implementa un banco de pruebas autoverificable
(\emph{self-checking}) de aproximadamente 540 líneas. Esta sección lo
descompone en capas y explica el propósito de cada una.

\subsection{Arquitectura del testbench}

La estrategia de verificación es la clásica de \emph{modelo de referencia}
(también llamado \emph{golden model} o \emph{bible model}): en paralelo al DUT
se mantiene una descripción independiente del comportamiento esperado, y ante
cada estímulo se comparan ambas salidas. La Figura~\ref{fig:tb} resume el flujo.

Un punto de método importante, señalado en el propio encabezado del archivo:
\textbf{el modelo de referencia describe la especificación, no la
implementación}. Si el DUT no implementara una operación, el testbench debe
reportarlo como error, no darlo por bueno. Se reconoce, no obstante, una
limitación inherente a un diseño tan simple: la especificación de cada
operación es tan directa (una única expresión Verilog) que el modelo termina
siendo estructuralmente parecido al \texttt{case} del DUT. La independencia real
se logra por dos vías complementarias: haber escrito el modelo a partir de la
Tabla~\ref{tab:ops} y no copiando el archivo, y complementarlo con el TEST 7,
donde los resultados esperados están calculados a mano y escritos como
constantes.

\subsection{Definiciones iniciales}

\subsubsection{Parámetros del entorno de prueba}

\begin{lstlisting}[caption={Parámetros del testbench.}]
localparam LENGTH_BITS = 16;
localparam LENGTH_OPT  = 6;
localparam SHAMT_BITS  = $clog2(LENGTH_BITS);
localparam N_RANDOM    = 500;
localparam PCT_OP_VALIDO = 85;

localparam TSETUP = 2;   // switch estable antes de pulsar
localparam TPRESS = 5;   // ancho del pulso del boton
localparam THOLD  = 2;   // espera antes de muestrear o_leds
\end{lstlisting}

Los tres retardos merecen explicación porque son la clave para poder reutilizar
el mismo testbench en las tres etapas de simulación exigidas por el enunciado:

\begin{itemize}[leftmargin=2em,itemsep=0.2em]
  \item \texttt{TSETUP}: tiempo durante el cual los switches permanecen estables
        \emph{antes} de que se active el pulsador. Emula el gesto real del
        operador (primero se configuran los switches, después se pulsa) y evita
        muestrear el latch mientras el bus está conmutando.
  \item \texttt{TPRESS}: ancho del pulso. Debe ser suficientemente largo como
        para que el latch, que es transparente por nivel, alcance a propagar el
        valor.
  \item \texttt{THOLD}: espera después de soltar el botón y antes de muestrear
        \texttt{o\_leds}. Es el tiempo que se le da a la lógica combinacional
        para estabilizarse.
\end{itemize}

En simulación funcional (\emph{behavioral}) los retardos podrían ser cero,
porque no hay demoras físicas. Están parametrizados porque en simulación
post-implementación el \emph{netlist} tiene retardos reales anotados en el
archivo SDF, y muestrear demasiado pronto produciría falsos negativos. Subiendo
estas tres constantes, el mismo banco de pruebas sirve sin modificaciones para
la simulación temporizada.

El parámetro \texttt{PCT\_OP\_VALIDO = 85} se justifica en la
Sección~\ref{sec:random}.

\subsubsection{Señales y estructuras de contabilidad}

\begin{lstlisting}[caption={Señales del testbench.}]
reg  [15:0] i_switch;
reg         i_button_1, i_button_2, i_button_3;
wire [LENGTH_BITS-1:0] o_leds;

// Modelo espejo: refleja lo que el DUT deberia tener guardado
reg [LENGTH_BITS-1:0] m_A, m_B;
reg [LENGTH_OPT-1:0]  m_opt;

integer errors, checks, i, seed;
reg     verbose;

reg [5:0] ops [0:N_OPS-1];     // tabla de opcodes validos
integer   cov [0:63];          // cobertura de los 64 opcodes
integer   cov_faltantes;
\end{lstlisting}

Las variables \texttt{m\_A}, \texttt{m\_B} y \texttt{m\_opt} constituyen el
\textbf{modelo espejo del estado}. El testbench no espía las señales internas
del DUT: mantiene su propia copia de lo que \emph{debería} estar almacenado,
actualizada por las mismas tareas que generan el estímulo. Esto es deliberado y
tiene una consecuencia valiosa: si el bloque de captura del DUT fallara —por
ejemplo, si la prioridad estuviera invertida— el modelo espejo y el DUT
divergirían y el error se detectaría, cosa que no ocurriría si el testbench
leyera \texttt{dut.dato\_A} directamente.

El arreglo \texttt{cov[0:63]} implementa una métrica de \textbf{cobertura
funcional} rudimentaria pero efectiva: cuenta cuántas veces se ejercitó cada uno
de los 64 opcodes posibles. Al final de la corrida permite responder la pregunta
que todo banco de pruebas debe responder: ¿realmente se probó todo lo que se
dice haber probado?

\subsection{Modelo de referencia}

\begin{lstlisting}[caption={Modelo de referencia \texttt{alu\_ref}.},label={lst:ref}]
function [LENGTH_BITS-1:0] alu_ref;
    input [LENGTH_BITS-1:0] a;
    input [LENGTH_BITS-1:0] b;
    input [LENGTH_OPT-1:0]  op;
    begin
        case (op)
            ADD:  alu_ref = a + b;
            SUB:  alu_ref = a - b;
            AND_: alu_ref = a & b;
            OR_:  alu_ref = a | b;
            XOR_: alu_ref = a ^ b;
            NOR_: alu_ref = ~(a | b);
            SRA:  alu_ref = $signed(a) >>> b[SHAMT_BITS-1:0];
            SRL:  alu_ref = a >> b[SHAMT_BITS-1:0];
            default: alu_ref = 16'd0;
        endcase
    end
endfunction
\end{lstlisting}

Se implementa como \texttt{function} y no como \texttt{task} porque devuelve un
valor y no consume tiempo de simulación: se evalúa instantáneamente en el
momento de la comparación. Es una función pura, sin efectos laterales, lo que
permite invocarla desde cualquier punto sin alterar el estado del banco de
pruebas.

\subsection{Funciones de utilidad}
\label{sec:util}

\subsubsection{\texttt{op\_name}: legibilidad de los mensajes}

\begin{lstlisting}[caption={Conversión de opcode a nombre legible.}]
function [8*8-1:0] op_name;
    input [LENGTH_OPT-1:0] op;
    begin
        case (op)
            ADD: op_name = "ADD";   SUB: op_name = "SUB";
            ...
            default: op_name = "INVALID";
        endcase
    end
endfunction
\end{lstlisting}

Devuelve un vector de $8 \times 8 = 64$ bits que Verilog interpreta como una
cadena de hasta ocho caracteres ASCII. Su única función es diagnóstica: un
mensaje de error que dice \texttt{op=100010 (SUB)} permite localizar el problema
mucho más rápido que uno que sólo muestre el binario. En una corrida de 500
vectores aleatorios, la calidad de los mensajes de error es lo que determina si
un fallo se depura en minutos o en horas.

\subsubsection{Generación aleatoria ponderada}
\label{sec:random}

Esta es la parte del testbench donde se concentra la mayor cantidad de decisiones
de diseño de verificación.

\begin{lstlisting}[caption={Sorteo de opcode con ponderación.},label={lst:randomop}]
function [5:0] random_op;
    input dummy;
    begin
        if (({$random(seed)} % 100) < PCT_OP_VALIDO)
            random_op = ops[{$random(seed)} % N_OPS];
        else
            random_op = $random(seed);
    end
endfunction
\end{lstlisting}

El problema que resuelve es de \textbf{eficiencia estadística}. Si se sortearan
los 6 bits de \texttt{opt} de forma uniforme, la probabilidad de caer en una
operación implementada sería

\[
P(\text{opcode válido}) = \frac{8}{64} = 12{,}5\%
\]

es decir que el $87{,}5\%$ de los vectores aleatorios estaría verificando una y
otra vez la misma rama \texttt{default}. Sobre 500 vectores, apenas unos 62
ejercitarían operaciones reales: alrededor de 8 por operación, una muestra
demasiado pobre. Con la ponderación al $85\%$ se obtienen del orden de 425
vectores sobre opcodes válidos (unos 53 por operación) y unos 75 sobre el
espacio completo de 6 bits, que siguen cubriendo la rama por defecto de forma
sobrada. La distribución de esfuerzo pasa a estar alineada con dónde está el
riesgo real de error.

\begin{lstlisting}[caption={Sorteo de datos con sesgo hacia valores borde.},label={lst:randomdata}]
function [15:0] random_data;
    input dummy;
    integer r;
    begin
        r = {$random(seed)} % 100;
        if      (r < 5)  random_data = 16'h0000;
        else if (r < 10) random_data = 16'hFFFF;
        else if (r < 15) random_data = 16'h8000;
        else if (r < 20) random_data = 16'h7FFF;
        else             random_data = $random(seed);
    end
endfunction
\end{lstlisting}

El mismo razonamiento se aplica a los operandos. Un sorteo uniforme de 16 bits
tiene probabilidad $2^{-16} \approx 1{,}5 \times 10^{-5}$ de producir
\texttt{0x0000}, y otro tanto para \texttt{0xFFFF}, \texttt{0x8000} y
\texttt{0x7FFF}. En 500 vectores es prácticamente seguro que ninguno de esos
valores aparezca nunca. Pero son exactamente los valores donde los errores se
esconden: el neutro de la suma, el desbordamiento del sumador, el mínimo entero
con signo (crítico para SRA, porque es el único con bit de signo en 1 y todos
los demás en 0) y el máximo entero con signo (donde $+1$ produce desbordamiento
con signo). Reservándoles un $5\%$ de probabilidad a cada uno, cada valor borde
aparece unas 25 veces por corrida en cada operando.

\paragraph{El idioma \texttt{\{\$random(seed)\}}.}
La llave de concatenación alrededor de la llamada no es decorativa.
\texttt{\$random} devuelve un entero \emph{con signo} de 32 bits, que la mitad
de las veces es negativo. En Verilog, el operador módulo con un operando
negativo devuelve un resultado negativo, lo que produciría índices negativos al
acceder a \texttt{ops[]} —comportamiento indefinido— y comparaciones erróneas
contra \texttt{PCT\_OP\_VALIDO}. Envolver la expresión en una concatenación la
fuerza a interpretarse como \emph{unsigned}, garantizando que el módulo caiga en
el rango esperado.

\paragraph{Reproducibilidad.} Todas las llamadas pasan la variable
\texttt{seed}, de modo que la secuencia pseudoaleatoria queda completamente
determinada por su valor inicial. Esto es un requisito de verificación, no una
comodidad: si una corrida falla, cambiar la semilla haría desaparecer el fallo y
sería imposible depurarlo. Con semilla fija, la corrida es exactamente
reproducible y el error puede reproducirse tantas veces como haga falta. La
semilla se imprime al comienzo de la simulación con la indicación explícita de
anotarla.

\subsection{Tareas de estímulo}

\begin{lstlisting}[caption={Tareas de carga de registros.},label={lst:load}]
task load_A;
    input [15:0] v;
    begin
        i_switch = v;
        #TSETUP i_button_1 = 1'b1;
        #TPRESS i_button_1 = 1'b0;
        #THOLD;
        m_A = v;              // actualiza el modelo espejo
    end
endtask
\end{lstlisting}

\texttt{load\_A}, \texttt{load\_B} y \texttt{load\_OPT} son idénticas salvo por
el pulsador que activan y el registro espejo que actualizan. Cada una reproduce
la secuencia física completa de una carga: colocar el valor en los switches,
esperar, pulsar, mantener, soltar, esperar la estabilización. Se implementan
como \texttt{task} y no como \texttt{function} precisamente porque consumen
tiempo de simulación, cosa que las funciones tienen prohibida.

La actualización del modelo espejo ocurre \emph{al final} de la tarea, después
de soltar el botón. Esto refleja la semántica real del latch: el valor queda
comprometido cuando la compuerta se cierra.

\texttt{load\_OPT} tiene una particularidad que documenta un detalle de la
interfaz:

\begin{lstlisting}[caption={Truncamiento del opcode en \texttt{load\_OPT}.}]
task load_OPT;
    input [15:0] v;
    begin
        i_switch = v;
        #TSETUP i_button_3 = 1'b1;
        #TPRESS i_button_3 = 1'b0;
        #THOLD;
        m_opt = v[LENGTH_OPT-1:0];   // solo los 6 bits bajos
    end
endtask
\end{lstlisting}

El bus de switches tiene 16 bits pero \texttt{opt} sólo 6. La asignación
\texttt{opt = i\_switch} del DUT trunca silenciosamente los 10 bits superiores.
El modelo espejo replica ese truncamiento de forma explícita, y el TEST 5 lo
verifica como un comportamiento especificado.

Finalmente, \texttt{load\_all} encapsula la secuencia completa de tres cargas,
que es el patrón que utilizan la mayoría de los tests:

\begin{lstlisting}[caption={Carga de los tres registros.}]
task load_all;
    input [15:0] a; input [15:0] b; input [5:0] op;
    begin
        load_A(a); load_B(b); load_OPT({10'b0, op});
    end
endtask
\end{lstlisting}

\subsection{Tareas de verificación}

El banco de pruebas ofrece dos mecanismos de chequeo complementarios.

\subsubsection{\texttt{check\_result}: comparación contra el modelo}

\begin{lstlisting}[caption={Chequeo contra el modelo de referencia.},label={lst:checkresult}]
task check_result;
    input [8*40-1:0] etiqueta;
    reg [LENGTH_BITS-1:0] esperado;
    begin
        esperado = alu_ref(m_A, m_B, m_opt);
        checks   = checks + 1;
        if (^m_opt !== 1'bx) cov[m_opt] = cov[m_opt] + 1;

        if (o_leds !== esperado) begin
            errors = errors + 1;
            $display("[FAIL] t=%0t %0s | op=%b (%0s) A=0x%h B=0x%h | esperado=0x%h obtenido=0x%h", ...);
        end
        else if (verbose) begin
            $display("[ OK ] ...");
        end
    end
endtask
\end{lstlisting}

Tres detalles de implementación:

\begin{itemize}[leftmargin=2em,itemsep=0.3em]
  \item \textbf{Comparación con \texttt{!==} y no con \texttt{!=}.} El operador
        \texttt{!==} es la desigualdad \emph{de caso}: distingue \texttt{0},
        \texttt{1}, \texttt{x} y \texttt{z} como cuatro valores diferentes. El
        operador \texttt{!=} devuelve \texttt{x} cuando alguno de los operandos
        contiene indeterminaciones, y ese \texttt{x} se evalúa como falso en la
        condición del \texttt{if}, con lo cual \textbf{un DUT que emitiera
        \texttt{16'hxxxx} pasaría el test sin ser detectado}. Usar \texttt{!==}
        garantiza que cualquier bit indeterminado en la salida se reporte como
        error.

  \item \textbf{Guarda de cobertura \texttt{\^{}m\_opt !== 1'bx}.} La reducción
        XOR sobre \texttt{m\_opt} da \texttt{x} si alguno de sus bits es
        indeterminado. Como \texttt{m\_opt} arranca en \texttt{6'bxxxxxx}, sin
        esta guarda el intento de indexar \texttt{cov[m\_opt]} con un índice
        indeterminado corrompería el arreglo de cobertura o abortaría la
        simulación según el simulador.

  \item \textbf{Verbosidad conmutable.} Con \texttt{verbose = 1} se imprimen
        también los casos exitosos, útil durante el desarrollo y para inspección
        manual. En el TEST 8 se baja a \texttt{0} porque 500 líneas de
        \texttt{[ OK ]} sepultarían cualquier \texttt{[FAIL]} en el log. Los
        fallos se imprimen siempre, en cualquier modo.
\end{itemize}

\subsubsection{\texttt{check\_value}: comparación contra un valor calculado a mano}

\begin{lstlisting}[caption={Chequeo contra un valor esperado explícito.}]
task check_value;
    input [8*40-1:0] etiqueta;
    input [LENGTH_BITS-1:0] esperado;
    begin
        checks = checks + 1;
        if (o_leds !== esperado) begin ... end
    end
endtask
\end{lstlisting}

Esta tarea \textbf{no utiliza el modelo de referencia}: recibe el valor esperado
como argumento. Su razón de ser es cubrir el punto ciego del enfoque de modelo
espejo: si el modelo y el DUT contuvieran el mismo error conceptual, la
comparación entre ambos no lo detectaría. Los valores de \texttt{check\_value}
están calculados manualmente a partir de la Tabla~\ref{tab:ops} y constituyen
una tercera fuente de verdad, independiente tanto del DUT como del modelo.

\subsubsection{\texttt{run\_op}: el patrón completo}

\begin{lstlisting}[caption={Ejecución y verificación de una operación.}]
task run_op;
    input [15:0] a; input [15:0] b; input [5:0] op;
    begin
        load_all(a, b, op);
        check_result("op");
    end
endtask
\end{lstlisting}

Reduce cada caso de prueba a una sola línea legible, lo que permite escribir el
TEST 7 como una lista compacta de casos borde en la que la intención de cada uno
se lee de un vistazo.

\subsection{Secuencia principal de pruebas}

\subsubsection{Inicialización}

\begin{lstlisting}[caption={Bloque \texttt{initial} de arranque.}]
initial begin
    errors = 0; checks = 0; verbose = 1'b1;
    seed   = 32'd02092026;
    i_switch = 16'h0000;
    i_button_1 = 1'b0; i_button_2 = 1'b0; i_button_3 = 1'b0;
    m_A = 16'hxxxx; m_B = 16'hxxxx; m_opt = 6'bxxxxxx;

    ops[0] = ADD;  ops[1] = SUB;  ops[2] = AND_;  ops[3] = OR_;
    ops[4] = XOR_; ops[5] = NOR_; ops[6] = SRA;   ops[7] = SRL;

    for (i = 0; i < 64; i = i + 1) cov[i] = 0;
    ...
\end{lstlisting}

Los tres registros espejo se inicializan deliberadamente en \texttt{x}, no en
cero, para que el modelo refleje con fidelidad el estado real del DUT tras el
encendido: sin reset, el contenido de los latches es desconocido. Inicializarlos
en cero sería una suposición no justificada que podría enmascarar un error.

\subsubsection{TEST 1 --- Estado inicial}

\begin{lstlisting}[caption={Documentación del estado sin inicializar.}]
$display("--- TEST 1: estado inicial (sin cargar nada) ---");
#20;
if (o_leds === {LENGTH_BITS{1'bx}})
    $display("[INFO] t=%0t Salida indefinida (X): los registros no tienen reset.", $time);
else
    $display("[INFO] t=%0t Salida = 0x%h sin haber cargado nada (default del case).", $time, o_leds);
\end{lstlisting}

\textbf{Qué busca:} documentar, no juzgar. Este test no incrementa el contador
de errores porque el comportamiento sin reset no está especificado; su función
es dejar constancia en el log de qué hace realmente el diseño al arrancar.

\textbf{Qué revela:} como se anticipó en la Sección~\ref{sec:case}, la salida
observada es \texttt{0x0000} y no \texttt{0xxxxx}, porque \texttt{opt = x} cae
en la rama \texttt{default}. La conclusión práctica —y el motivo por el que este
test existe— es que \emph{el cero de arranque es indistinguible de un resultado
válido de valor cero}. Un operador que encienda la placa y vea todos los LEDs
apagados no puede saber si la ALU está sin configurar o si acaba de calcular un
cero legítimo. Es una observación de usabilidad que conviene tener presente.

\subsubsection{TEST 2 --- Carga individual de registros}

\begin{lstlisting}
load_A(16'h1234); load_B(16'h0001); load_OPT({10'b0, ADD});
check_value("carga A=0x1234 B=0x0001 ADD", 16'h1235);

load_A(16'hFFFF);
check_value("recarga A=0xFFFF (ADD)", 16'h0000);   // 0xFFFF + 1, overflow

load_B(16'h0002);
check_value("recarga B=0x0002 (ADD)", 16'h0001);
\end{lstlisting}

\textbf{Qué busca:} validar el camino de datos básico, que es la precondición de
todo lo demás. Verifica tres propiedades:

\begin{enumerate}[leftmargin=2em,itemsep=0.15em]
  \item Que cada pulsador escribe en el registro correcto (si \texttt{button\_1}
        escribiera en \texttt{dato\_B}, el primer chequeo fallaría).
  \item Que la recarga de un registro no altera los otros dos: tras recargar
        \texttt{A}, la operación sigue siendo ADD y \texttt{B} sigue valiendo 1.
  \item Que el sumador descarta el acarreo de salida:
        $\texttt{0xFFFF} + 1 = \texttt{0x0000}$ en aritmética de 16 bits.
\end{enumerate}

Se usa \texttt{check\_value} y no \texttt{check\_result} porque los tres valores
esperados se calcularon a mano.

\subsubsection{TEST 3 --- Retención y transparencia del latch}
\label{sec:test3}

\begin{lstlisting}[caption={Verificación del comportamiento del latch.}]
load_all(16'h00F0, 16'h000F, OR_);
check_value("A=0x00F0 B=0x000F OR", 16'h00FF);

// Los switches cambian pero ningun boton esta apretado
i_switch = 16'hDEAD; #10;
check_value("switch cambia sin botones -> sin efecto", 16'h00FF);
i_switch = 16'h0000; #10;
check_value("switch en 0 sin botones -> sin efecto", 16'h00FF);

// Transparencia: el switch cambia CON el boton apretado
i_switch = 16'h1111;
#TSETUP i_button_1 = 1'b1;
#3      i_switch   = 16'h2222;   // cambia con el boton apretado
#3      i_button_1 = 1'b0;
#THOLD;
m_A = 16'h2222;
check_result("latch transparente (gana el ultimo valor)");
\end{lstlisting}

\textbf{Qué busca:} este es el test que valida directamente la estructura física
descripta en la Sección~\ref{sec:ifelse}, y tiene dos mitades.

La primera mitad verifica la \textbf{retención}: se hacen variar los switches de
forma agresiva (\texttt{0xDEAD}, luego \texttt{0x0000}) sin tocar ningún
pulsador, y se comprueba que la salida no se mueve. Si el sintetizador no
hubiera inferido latches —o si el bloque hubiera sido escrito de forma que
\texttt{dato\_A} siguiera continuamente a \texttt{i\_switch}— la salida cambiaría
y el test fallaría. Es la comprobación de que los elementos de memoria existen y
funcionan.

La segunda mitad verifica la \textbf{transparencia}, que es la contracara del
mismo fenómeno. Con el pulsador activo, el latch está abierto y sigue a la
entrada; por lo tanto lo que queda guardado no es \texttt{0x1111} (el valor al
apretar) sino \texttt{0x2222} (el valor al soltar). Este comportamiento
distingue un \emph{latch} de un \emph{flip-flop}: con un flip-flop disparado por
flanco habría quedado guardado \texttt{0x1111}. El test convierte esa diferencia
en un requerimiento verificable, de modo que si alguien reescribiera el bloque
con \texttt{always @(posedge i\_button\_1)} el cambio quedaría documentado por
una falla del test y no pasaría inadvertido.

\subsubsection{TEST 4 --- Prioridad entre pulsadores}

\begin{lstlisting}[caption={Verificación del codificador de prioridad.}]
load_all(16'h1111, 16'h2222, ADD);
check_value("base A=0x1111 B=0x2222 ADD", 16'h3333);

// btn1 + btn2 juntos -> por prioridad, solo carga A
i_switch = 16'hAAAA;
#TSETUP i_button_1 = 1'b1; i_button_2 = 1'b1;
#TPRESS i_button_1 = 1'b0; i_button_2 = 1'b0;
#THOLD; m_A = 16'hAAAA;                        // B NO cambia
check_value("btn1+btn2 -> solo carga A", 16'hCCCC);   // AAAA + 2222

// btn2 + btn3 juntos -> solo carga B
i_switch = 16'h0001;
#TSETUP i_button_2 = 1'b1; i_button_3 = 1'b1;
#TPRESS i_button_2 = 1'b0; i_button_3 = 1'b0;
#THOLD; m_B = 16'h0001;                        // opt NO cambia, sigue ADD
check_value("btn2+btn3 -> solo carga B", 16'hAAAB);

// los tres a la vez -> solo carga A
i_switch = 16'h0002;
#TSETUP i_button_1 = 1'b1; i_button_2 = 1'b1; i_button_3 = 1'b1;
#TPRESS i_button_1 = 1'b0; i_button_2 = 1'b0; i_button_3 = 1'b0;
#THOLD; m_A = 16'h0002;
check_value("btn1+btn2+btn3 -> solo carga A", 16'h0003);
\end{lstlisting}

\textbf{Qué busca:} verificar el orden de prioridad entre los pulsadores
resumido en la Tabla~\ref{tab:prioridad}. El test es
particularmente elegante porque \textbf{comprueba a la vez lo que sí ocurre y lo
que no debe ocurrir}, usando la propia operación de la ALU como sonda.

Tomemos el segundo caso. Se pulsan \texttt{btn1} y \texttt{btn2} juntos con
\texttt{0xAAAA} en los switches. Se espera $\texttt{0xAAAA} + \texttt{0x2222} =
\texttt{0xCCCC}$, lo cual sólo es cierto si simultáneamente:

\begin{itemize}[leftmargin=2em,itemsep=0.15em]
  \item \texttt{dato\_A} \emph{sí} se actualizó a \texttt{0xAAAA} (prioridad de
        \texttt{btn1}), y
  \item \texttt{dato\_B} \emph{no} se actualizó y conserva \texttt{0x2222}
        (bloqueo de \texttt{btn2}).
\end{itemize}

Si la prioridad estuviera invertida se obtendría $\texttt{0x1111} +
\texttt{0xAAAA} = \texttt{0xBBBB}$; si ambos se escribieran (versión sin
prioridad del Código~\ref{lst:noprio}) se obtendría $\texttt{0xAAAA} +
\texttt{0xAAAA} = \texttt{0x5554}$. Cada comportamiento posible produce un
resultado distinguible. La misma lógica gobierna el tercer caso (\texttt{btn2}
gana sobre \texttt{btn3}: si \texttt{opt} se hubiera sobreescrito con
\texttt{0x0001}, ese opcode no está implementado y la salida sería
\texttt{0x0000} en lugar de \texttt{0xAAAB}) y el cuarto (los tres pulsadores a
la vez, donde sólo \texttt{A} debe cambiar).

\subsubsection{TEST 5 --- Truncamiento del opcode}

\begin{lstlisting}
load_A(16'h000C);
load_B(16'h000A);
load_OPT(16'hFFE2);   // bits [5:0] = 100010 = SUB
check_value("switch=0xFFE2 -> opt=100010 (SUB)", 16'h0002);
\end{lstlisting}

\textbf{Qué busca:} confirmar que los 10 bits superiores del bus de switches se
descartan al cargar \texttt{opt}. Se elige \texttt{0xFFE2} = \texttt{1111 1111
1110 0010}, cuyos seis bits bajos son \texttt{100010} (SUB) y cuyos diez bits
altos están todos en 1, la condición más adversa posible. El resultado esperado
$\texttt{0x000C} - \texttt{0x000A} = 12 - 10 = 2$ sólo se obtiene si el
truncamiento es correcto. Es un test corto pero necesario, porque el
truncamiento por asignación de anchos distintos es silencioso en Verilog: no
genera advertencia y es una fuente clásica de errores.

\subsubsection{TEST 6 --- Barrido exhaustivo de opcodes}

\begin{lstlisting}
load_A(16'h00F0);
load_B(16'h000F);
for (i = 0; i < 64; i = i + 1) begin
    load_OPT({10'b0, i[5:0]});
    check_result("barrido");
end
\end{lstlisting}

\textbf{Qué busca:} cobertura exhaustiva del espacio del selector. Como
$2^6 = 64$ es un número pequeño, es posible probar \emph{todos} los opcodes sin
recurrir a muestreo. Este test garantiza que:

\begin{itemize}[leftmargin=2em,itemsep=0.15em]
  \item Las 8 operaciones definidas producen el resultado correcto.
  \item Los 56 opcodes no definidos producen \texttt{0x0000} y no un valor
        residual, un \texttt{x}, o el resultado de otra operación por un error
        de decodificación.
\end{itemize}

Los operandos elegidos, \texttt{0x00F0} y \texttt{0x000F}, no son arbitrarios:
son \emph{disjuntos en bits}, de modo que cada operación lógica arroja un
resultado distinto y fácilmente distinguible (AND $\to$ \texttt{0x0000}, OR
$\to$ \texttt{0x00FF}, XOR $\to$ \texttt{0x00FF}, NOR $\to$ \texttt{0xFF00},
ADD $\to$ \texttt{0x00FF}, SUB $\to$ \texttt{0x00E1}). Además \texttt{0x000F}
como \texttt{dato\_B} equivale a un desplazamiento de 15 posiciones, el máximo
posible, lo que ejercita el barrel shifter en su configuración extrema.

\subsubsection{TEST 7 --- Casos borde por operación}

Este test es el más extenso y está organizado en un bloque por operación. Los
valores esperados están anotados en comentarios y calculados manualmente. La
Tabla~\ref{tab:borde} resume la intención de los casos más significativos.

\begin{longtable}{llp{7.4cm}}
  \toprule
  \textbf{Op.} & \textbf{Caso} & \textbf{Qué verifica} \\
  \midrule
  \endhead
  ADD & \texttt{0x0000 + 0x0000} & Elemento neutro; salida totalmente en cero. \\
  ADD & \texttt{0xFFFF + 0x0001} & Desbordamiento sin signo: el acarreo de salida se descarta y el resultado es \texttt{0x0000}. \\
  ADD & \texttt{0xFFFF + 0xFFFF} & Máximo desbordamiento; verifica la cadena de acarreo completa. \\
  ADD & \texttt{0x7FFF + 0x0001} & Desbordamiento \emph{con signo}: $+32767 + 1 \to \texttt{0x8000} = -32768$. \\
  ADD & \texttt{0x8000 + 0x8000} & $-32768 + (-32768) \to \texttt{0x0000}$. \\
  \midrule
  SUB & \texttt{0x0003 - 0x0005} & Préstamo (\emph{underflow}): $\to \texttt{0xFFFE} = -2$. Valida el complemento a dos. \\
  SUB & \texttt{0x0000 - 0x0001} & $\to \texttt{0xFFFF} = -1$, el caso canónico de préstamo. \\
  SUB & \texttt{0x8000 - 0x0001} & Cruce del límite negativo $\to \texttt{0x7FFF}$. \\
  SUB & \texttt{0xFFFF - 0xFFFF} & Cancelación exacta $\to \texttt{0x0000}$. \\
  \midrule
  AND & \texttt{0xAAAA \& 0x5555} & Patrones complementarios alternados $\to \texttt{0x0000}$: ningún bit ``se filtra'' de una posición a otra. \\
  AND & \texttt{0xF0F0 \& 0xFF00} & Enmascaramiento parcial $\to \texttt{0xF000}$. \\
  OR  & \texttt{0xAAAA | 0x5555} & Cobertura completa $\to \texttt{0xFFFF}$. \\
  XOR & \texttt{0xFFFF \^{} 0xFFFF} & Autocancelación $\to \texttt{0x0000}$. \\
  XOR & \texttt{0x1234 \^{} 0x0000} & Elemento neutro del XOR. \\
  NOR & \texttt{0x0000 nor 0x0000} & $\to \texttt{0xFFFF}$: verifica la inversión sobre todos los bits. \\
  \midrule
  SRL & \texttt{0x8000 >> 15} & Desplazamiento máximo: el bit más significativo llega al menos significativo $\to \texttt{0x0001}$. \\
  SRL & \texttt{0xFFFF >> 0}   & Desplazamiento nulo: la salida debe ser idéntica a la entrada. \\
  SRL & \texttt{0xABCD >> 4}   & Desplazamiento de un nibble $\to \texttt{0x0ABC}$, fácil de verificar visualmente. \\
  \midrule
  SRA & \texttt{0xF000 >>> 2}  & Operando negativo: debe replicar el signo $\to \texttt{0xFC00}$, no \texttt{0x3C00}. \\
  SRA & \texttt{0x8000 >>> 15} & Caso extremo: $-32768$ desplazado al máximo $\to \texttt{0xFFFF} = -1$. \\
  SRA & \texttt{0x7FFF >>> 1}  & Operando positivo: SRA debe coincidir con SRL $\to \texttt{0x3FFF}$. \\
  SRA & \texttt{0x8000 >>> 1}  & Un solo desplazamiento con signo $\to \texttt{0xC000}$. \\
  \midrule
  --- & \texttt{opt = 000000} & Opcode nulo. \\
  --- & \texttt{opt = 111111} & Opcode con todos los bits en 1. \\
  --- & \texttt{opt = 100001} & Adyacente a ADD (\texttt{100000}): detecta errores de decodificación por un bit. \\
  --- & \texttt{opt = 101010} & Corresponde a SLT en MIPS; no implementado aquí. \\
  --- & \texttt{opt = 101011} & Corresponde a SLTU en MIPS; tampoco implementado. \\
  \bottomrule
  \caption{Casos borde del TEST 7 y su propósito.}
  \label{tab:borde}
\end{longtable}

El par SRA/SRL merece un comentario aparte porque es donde se concentra el
riesgo de error del diseño. La comparación \texttt{0xF000 >>> 2} $\to$
\texttt{0xFC00} contra \texttt{0xF000 >> 2} $\to$ \texttt{0x3C00} es la que
distingue si el desplazamiento aritmético está bien implementado. En Verilog el
operador \texttt{>>>} realiza extensión de signo \emph{únicamente si el operando
izquierdo está declarado como \texttt{signed}}; sin la conversión explícita
\texttt{\$signed(dato\_A)} el operador se comporta exactamente igual que
\texttt{>>} y el error pasaría inadvertido con operandos positivos. El caso
\texttt{0x7FFF >>> 1}, donde SRA y SRL deben coincidir, es la comprobación
complementaria: verifica que la extensión de signo no se aplique cuando no
corresponde.

Los cinco opcodes inválidos elegidos tampoco son arbitrarios:
\texttt{100001} está a distancia de Hamming 1 de ADD, lo que detecta un error de
un solo bit en el decodificador; \texttt{101010} y \texttt{101011} corresponden
a SLT y SLTU en el repertorio MIPS, operaciones que un lector podría suponer
implementadas y que aquí explícitamente no lo están.

\subsubsection{TEST 8 --- Vectores aleatorios}

\begin{lstlisting}[caption={Bucle de prueba aleatoria.}]
verbose = 1'b0;                 // solo se imprimen los FAIL
for (i = 0; i < N_RANDOM; i = i + 1) begin
    load_all(random_data(0), random_data(0), random_op(0));
    check_result("aleatorio");
    #(({$random(seed)} % 5) + 1);   // separacion variable entre vectores
end
verbose = 1'b1;
\end{lstlisting}

\textbf{Qué busca:} cumplir el requisito explícito del enunciado de generación
aleatoria con chequeo automático, y cubrir combinaciones de operandos que un
conjunto de casos escrito a mano nunca alcanzaría. Los 500 vectores exploran el
espacio $A \times B \times \mathrm{op}$ con la distribución sesgada descripta en
la Sección~\ref{sec:random}.

El retardo aleatorio entre vectores, \texttt{\#((\{\$random(seed)\} \% 5) + 1)},
introduce \textbf{variabilidad temporal} deliberada. Su valor está en la
simulación post-implementación: si los estímulos estuvieran siempre alineados
sobre la misma grilla temporal, ciertos solapamientos entre la propagación de la
lógica combinacional y la apertura de los latches nunca se producirían. Al
desalinear las cargas se ejercitan relaciones de fase que un patrón regular
dejaría fuera.

\subsubsection{Cobertura y reporte final}

\begin{lstlisting}[caption={Reporte de cobertura y resumen.}]
cov_faltantes = 0;
for (i = 0; i < N_OPS; i = i + 1) begin
    $display("   %0s (%b) : %0d veces", op_name(ops[i]), ops[i], cov[ops[i]]);
    if (cov[ops[i]] == 0) cov_faltantes = cov_faltantes + 1;
end
if (cov_faltantes != 0)
    $display("   [AVISO] %0d operaciones nunca se ejercitaron.", cov_faltantes);
...
$display("   Verificaciones : %0d", checks);
$display("   Errores        : %0d", errors);
if (errors == 0) $display("   RESULTADO : *** TODOS LOS TESTS PASARON ***");
else             $display("   RESULTADO : *** %0d TESTS FALLARON ***", errors);
\end{lstlisting}

El reporte de cobertura responde a una preocupación metodológica concreta:
\textbf{un testbench que no falla no demuestra nada si además no probó nada}. Si
por un error en la generación aleatoria alguna operación nunca llegara a
ejercitarse, el resumen diría igualmente ``todos los tests pasaron''. El aviso
de operaciones no cubiertas cierra esa brecha.

El resumen final imprime la cantidad total de verificaciones y errores, con un
veredicto explícito. Este formato es el que permite integrar el banco de pruebas
en un flujo automatizado: basta con buscar la cadena \texttt{TESTS FALLARON} en
el log para saber si la corrida fue exitosa.

\paragraph{Inconsistencia detectada.} En la versión actual del código, la línea
del resumen que imprime la semilla usa un literal (\texttt{32'd20260830}) en
lugar de la variable \texttt{seed} (que vale \texttt{32'd02092026}). El valor
reportado al final no coincide con el que efectivamente gobernó la corrida ni
con el que se imprime en el encabezado. No afecta al resultado de la
verificación, pero sí compromete la reproducibilidad si alguien anotara la
semilla del resumen. La corrección es reemplazar el literal por la variable:

\end{lstlisting}

\subsubsection{Temporizador de seguridad (\emph{watchdog})}

\begin{lstlisting}[caption={Bloque de timeout.}]
initial begin
    #500000;
    $display("[ERROR] Timeout: la simulacion no termino a tiempo.");
    $finish;
end
\end{lstlisting}

Este bloque \texttt{initial} corre en paralelo al principal y garantiza que la
simulación termine siempre. Sin él, un bloqueo —por ejemplo un lazo que nunca
avanza el tiempo de simulación— dejaría el simulador corriendo indefinidamente,
lo que en un flujo automatizado equivale a un cuelgue silencioso. Con el
watchdog, ese escenario se convierte en un mensaje de error explícito y una
terminación limpia. El valor de $5 \times 10^5$~ns es holgado frente a la
duración estimada de la corrida completa (del orden de $10^4$~ns), de modo que
no puede dispararse en una ejecución normal.

\section{Conclusiones}
% ============================================================

Se implementó una ALU de 16 bits parametrizable con las ocho operaciones
requeridas por el enunciado, y se la validó mediante un banco de pruebas
autoverificable con generación aleatoria de estímulos y medición de cobertura.

Las conclusiones principales del trabajo son:

\begin{itemize}[leftmargin=2em,itemsep=0.35em]
  \item \textbf{La elección entre \texttt{case} e \texttt{if / else} no es una
        cuestión de estilo.} Cada una describe una estructura de hardware
        distinta. El \texttt{case} describe una selección entre alternativas sin
        orden, que se implementa como un árbol de multiplexores; la cadena
        \texttt{if / else} describe una prioridad, que se implementa como
        multiplexores encadenados. En el núcleo operacional, donde las ocho
        operaciones son alternativas equivalentes, el \texttt{case} es la
        construcción adecuada.

  \item \textbf{La prioridad, cuando se la busca a propósito, es una decisión de
        diseño válida.} En el bloque de captura ocurre lo contrario: sí hay una
        relación de orden que se quiere imponer, porque interesa que un solo
        registro se escriba por pulsación. La cadena \texttt{if / else}
        convierte un comportamiento que de otro modo sería ambiguo (apretar dos
        botones a la vez) en un contrato explícito, que además el testbench
        puede verificar.

  \item \textbf{La forma de escribir el código determina qué elementos de
        memoria aparecen.} Al no haber reloj en la interfaz del enunciado y al
        no asignarse todas las variables en todos los caminos, el sintetizador
        infiere latches. Identificamos la limitación y sus consecuencias —el
        valor guardado es el que hay al soltar el botón, no al apretarlo—, pero
        resolverla requeriría incorporar un reloj de sistema junto con lógica de
        sincronización y filtrado de rebotes, que excede el alcance de este
        trabajo.

  \item \textbf{El banco de pruebas requiere tanto diseño como el circuito.} El
        modelo de referencia, los valores calculados a mano, el sesgo hacia
        valores borde en la generación aleatoria, la semilla fija y la medición
        de cobertura son lo que diferencia un testbench que efectivamente
        detecta errores de uno que los deja pasar sin ruido.
\end{itemize}

Finalmente, el trabajo deja documentadas de forma explícita las limitaciones
detectadas —ausencia de reset, falta de sincronización y filtrado de rebotes en
los pulsadores, y los literales de ancho fijo señalados en la
Sección~\ref{sec:paramobs}— que conviene corregir antes de reutilizar el módulo
en el trabajo final de la materia.

\appendix
\section{Código fuente de la ALU}
\label{ap:alu}
% ============================================================

\begin{lstlisting}[caption={\texttt{ALU.v} completo.}]
`timescale 1ns / 1ps

module ALU#
(
    parameter LENGTH_BITS = 16,
    parameter LENGTH_OPT  = 6
)
(
    output wire [LENGTH_BITS-1 : 0] o_leds,

    input wire [LENGTH_BITS-1:0] i_switch,
    (* clock_buffer_type = "none" *) input wire i_button_1,
    (* clock_buffer_type = "none" *) input wire i_button_2,
    (* clock_buffer_type = "none" *) input wire i_button_3
    );

    reg [LENGTH_BITS-1 : 0] result;
    reg [LENGTH_BITS-1 : 0] dato_A = 16'b0;
    reg [LENGTH_BITS-1 : 0] dato_B = 16'b0;
    reg [LENGTH_OPT-1  : 0] opt    = 6'b0;
    reg error_signal = 1'b0;

    //--------------------------------------------- Parametros locales
    localparam [5:0] ADD  = 6'b100000,
                     SUB  = 6'b100010,
                     AND_ = 6'b100100,
                     OR_  = 6'b100101,
                     XOR_ = 6'b100110,
                     NOR_ = 6'b100111,
                     SRA  = 6'b000011,
                     SRL  = 6'b000010;

    localparam SHAMT_BITS = $clog2(LENGTH_BITS);

    always @(*) begin
        if(i_button_1)       dato_A = i_switch;
        else if (i_button_2) dato_B = i_switch;
        else if (i_button_3) opt    = i_switch;
    end

    always @(*) begin
        case (opt)
            ADD:  result = dato_A + dato_B;
            SUB:  result = dato_A - dato_B;
            AND_: result = dato_A & dato_B;
            OR_:  result = dato_A | dato_B;
            XOR_: result = dato_A ^ dato_B;
            NOR_: result = ~(dato_A | dato_B);
            SRA:  result = $signed(dato_A) >>> dato_B[SHAMT_BITS-1:0];
            SRL:  result = dato_A >> dato_B[SHAMT_BITS-1:0];
            default: result = 16'd0;
        endcase
    end

    assign o_leds = result;

endmodule
\end{lstlisting}

\textbf{Nota:} el registro \texttt{error\_signal} está declarado pero nunca se
asigna ni se utiliza. El sintetizador lo elimina por optimización, de modo que
no genera hardware, pero conviene removerlo del código o bien darle uso (por
ejemplo, activarlo en la rama \texttt{default} para señalizar un opcode
inválido).
